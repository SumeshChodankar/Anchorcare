# AnchorCare + Engram

AnchorCare's original React/TypeScript prototype with Engram's MongoDB retrieval and proactive-trigger component integrated into the Express backend. Conversational answers are generated by **Meta Llama 4 Maverick**, which replaces the earlier Gemini Argon model.

## Run

Requires Node.js 22.12+ (tested with 24.22.1). Vite 8 does not support the previously installed Node 20.18 runtime.

```sh
npm ci --ignore-scripts --no-audit --no-fund
# Copy .env.example to a private .env and configure it locally.
npm run dev
```

Open http://127.0.0.1:3000 and choose **Open persistent memory workspace**. Enter the private `ANCHORCARE_ADMIN_KEY` for caregiver actions or `ANCHORCARE_COMPANION_KEY` for patient reads/responses. Keys remain in page memory and are not put in localStorage. The React role switcher in the original demo does not grant server caregiver permissions.

For real Atlas storage set `STORE=mongodb` and configure `MONGODB_URI`. Keep `ANCHORCARE_PATIENT_ID` in `SUBJECT_IDS`; the bridge uses this server-configured patient and ignores client-supplied patient IDs. Set distinct strong `ADMIN_TOKEN`/`COMPANION_TOKEN` and separate `ANCHORCARE_ADMIN_KEY`/`ANCHORCARE_COMPANION_KEY` values. Never commit `.env`. The server binds to loopback by default.

### Model configuration (Meta Llama)

Set the Meta model and provider in `.env`:

```sh
LLM_PROVIDER=meta    # meta (Meta Model API), openrouter, or ollama
META_MODEL=meta-llama/Llama-4-Maverick-17B-128E-Instruct  # exact ID format varies by provider
META_API_KEY=<private key>  # not needed for local Ollama
```

The same Llama model family can be served three ways without code changes: Meta's hosted Meta Model API (formerly the Llama API), OpenRouter, or self-hosting. Llama 4 Maverick needs data-centre GPUs to self-host; for a laptop or small local server, use a smaller Llama model through Ollama (see [FREE-MODEL-SETUP.md](FREE-MODEL-SETUP.md)). Gemini settings are preserved and can be switched back on by changing the provider.

## What is connected

- **`engram-retrieval/`** contains Athul's tested backend component, copied from `4thul-jk/Engram-Hackathon` at commit `22b37bb`, including its tests, setup scripts and documentation.
- **`integration/engram.ts`** mounts `/api/engram/*` inside AnchorCare's Express process. The same process connects to Atlas and runs the reminder worker. No second server or database credentials in browser code are required.
- **`src/components/EngramMemoryView.tsx`** provides source-backed draft ingestion, caregiver approval/withdrawal, unified memory retrieval, optional Llama answers and approved reminder creation/cancellation/responses.
- **`/api/engram/answer`** retrieves evidence on the server; it does not trust browser-supplied evidence. With no model provider configured it explicitly returns `evidence_only`, not a fake model answer. With a key it uses `META_MODEL`, structured JSON output and typed citation membership checks, with a fresh retrieval before response.
- Existing daily/person records and context-trigger endpoints are mounted and documented in the component. Stream Processing remains prepared but not deployed; `CONTEXT_PROCESSING` stays local.
- The main **Memory Ledger** loads/saves through Atlas-backed routes with review and correction history. The main **Patient Companion** now asks the authenticated server, which selects Atlas records by question/time and displays evidence plus current reminders. Original browser companion/ledger examples remain collapsed separately. Policy & Actions and the Python reference view are still browser demos, not migrated server workflows. No browser sample data is silently promoted into approved memory.

## Why Meta Llama, and where else it helps

Llama's main advantage for this project is that it is an **open-weight model family**: the same models can run on Meta's hosted API, through OpenRouter, or on infrastructure the care provider controls. For a memory-care tool handling sensitive personal information, that flexibility matters. Beyond the companion answers it already powers, Llama is useful in several other places:

- **Private, self-hosted deployment.** Self-hosting Llama (Llama 4 on a care provider's GPU server, or a smaller Llama model through Ollama on ordinary hardware) keeps patient memories, questions and pictures under the care home's or family's control, with no data sent to a third-party API. This is the strongest path towards a privacy-respecting production setup.
- **Offline resilience.** A locally hosted model keeps the companion answering when the internet connection drops, which matters for a patient who relies on it for reassurance.
- **No per-request cost.** Local or free-tier Llama makes frequent, repetitive companion questions ("Who is visiting today?") affordable, which suits patients who ask the same question many times a day.
- **Safety filtering with Llama Guard.** Meta's Llama Guard models can screen companion replies and caregiver inputs for unsafe or distressing content before they reach the patient, as an extra layer alongside citation checks.
- **Picture descriptions.** Llama 4 is natively multimodal, so it can draft captions for uploaded family pictures ("Two people at a beach, one holding a dog") so caregivers have a starting point. Drafts still require caregiver approval before entering memory.
- **Multilingual companions.** Llama supports several languages, so the companion can answer in the patient's first language, which can matter as dementia progresses and people return to their earliest language.
- **Caregiver handoff summaries.** Llama can summarise a day's records, reminder responses and approved memories into a short handoff note for the next caregiver shift, with citations back to the source records.
- **Drafting memories from notes.** A caregiver's free-text notes can be turned into structured draft memory entries (person, relationship, date, event) for review, saving typing while keeping a human in the loop.
- **On-device use.** Smaller Llama models are compact enough to explore running on the paired phone receiver for simple reminder phrasing without a server round-trip.
- **Fine-tuning.** Because the weights are open, a model could later be adapted to a gentle, consistent companion tone using synthetic conversations, without depending on a single vendor.

None of these change the project's boundaries below: model output is always drafted or evidence-backed, never treated as clinical advice, and nothing enters approved memory without caregiver review.

## Important boundaries

This is a local synthetic-data integration. Entered keys are shared prototype credentials, not production user authentication. Production needs individual sessions, patient/guardian authorization and HTTPS before external access. The server-selected single patient does not implement a multi-patient login system.

No audio/video upload, face recognition, guardian calling, emergency response or clinical decision system is added. The SOS link sends a browser alert to paired caregiver devices only; it does not contact emergency services. Citation/quote membership does not prove semantic support. Medical self-reports and plans retain their meaning; no medication instructions are executed. The old client-context `/api/gemini/reason` endpoint is disabled with HTTP 410. `/api/engram/ask` retrieves its own evidence and optionally invokes the configured Llama model; a model outage is shown as failure, not silently replaced with browser sample answers.

Long-running operations can still overlap approval changes; refreshed citations reduce, but do not eliminate, races. Server ledger corrections now use a MongoDB transaction covering original/replacement/source/audit writes; replacements begin as drafts. Browser demo correction tests alone do not prove this behaviour; a separate live HTTP/Atlas correction check has passed.

## Fictional medication reminder demo

See the medication demo guide for simulation data, caregiver approval, timed reminders, patient responses and caregiver review. Seed with `npm run demo:seed-medication`. All medication details are fictional; patient responses are reports, not proof of ingestion.

## Automatic model recovery

The Patient Companion uses cancellable background reply jobs with bounded transient-error retries and fresh evidence checks, for whichever model provider is configured. See the model recovery notes for endpoints, limits and verification. Jobs are in memory and do not survive server restart.

## Familiar people and memory pictures

Caregiver tools support picture uploads and approval. The companion retrieves matching approved pictures from MongoDB GridFS. See image recall. Seed labelled fictional illustrations with `npm run demo:seed-images`; upload real authorised family pictures through the caregiver panel.

## Phone receiver and SOS links

Open `/phone` on a phone on the same Wi-Fi and pair it from caregiver tools. Approved pictures can forward automatically, and caregiver/demo receivers can receive SOS browser alerts. Actual voice calls require private provider setup and explicit enabling; real calls are disabled in the demo.
